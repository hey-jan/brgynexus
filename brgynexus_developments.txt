========================================
PHASE 5: DATABASE DESIGN
========================================

Detailed Tables:

users
- user_id (PK)
- first_name
- middle_name
- last_name
- email
- password_hash
- phone
- role (resident / staff / admin)
- created_at

residents_profile
- resident_id (PK)
- user_id (FK → users.user_id)
- gender
- address
- birthdate
- civil_status
- is_verified

documents
- document_id (PK)
- document_name
- description
- fee
- processing_days
- is_active

document_requests
- request_id (PK)
- resident_id (FK → residents_profile.resident_id)
- document_id (FK → documents.document_id)
- purpose
- status (pending / approved / rejected / released)
- request_date
- updated_at
- released_at
- handled_by (FK → users.user_id)

request_status_logs
- log_id (PK)
- request_id (FK → document_requests.request_id)
- status
- remarks
- changed_by (FK → users.user_id)
- timestamp

issued_documents
- issued_id (PK)
- request_id (FK → document_requests.request_id)
- document_number
- qr_code_hash
- issued_date
- expiry_date

payments
- payment_id (PK)
- request_id (FK → document_requests.request_id)
- amount
- payment_method (cash / gcash / other)
- reference_number
- paid_at
- received_by (FK → users.user_id, nullable)

staff_assignments
- assignment_id (PK)
- user_id (FK → users.user_id)
- position (secretary / clerk / admin officer etc.)
- is_active

audit_logs
- audit_id (PK)
- user_id (FK → users.user_id)
- action
- details
- timestamp

relationships
- users 1–1 residents_profile
- users 1–many document_requests (via handled_by)
- users 1–many payments (via received_by)
- users 1–many audit_logs
- users 1–many request_status_logs (via changed_by)
- users 1–many staff_assignments

- residents_profile 1–many document_requests
- documents 1–many document_requests

- document_requests 1–many request_status_logs
- document_requests 1–1 issued_documents
- document_requests 1–1 payments

- Add optional:
  - email_logs (SendGrid)
  - latitude / longitude (Google Maps)
